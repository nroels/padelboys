WHAT IT COSTS TO BUILD

  • Schema — one column: game_nights.at_cronos boolean not null default true. The dropped Cronos integration only removed court/source/sharepoint_item_id, so nothing conflicts.
  • Maths — hours = (ends_at - starts_at) / 3600, savings = hours * 20 when at_cronos. Pure function in src/lib/, unit-testable like stats.js.
  • Banked vs pending — count a night once it is finished; show upcoming Cronos nights as pending so the number does not lie.
  • Nulls — ends_at is nullable on old rows. Either skip those nights or assume 1.5h; skipping is honest, assuming is friendlier. Backfilled history rows have no venue either — default them to non-Cronos so the pool only counts what you know.

TRADE-OFFS

  • A is the strongest arcade moment but eats the home screen, and the pool competes with the ranking for attention. Best if the savings are meant to drive behaviour.
  • B costs ~30px of chrome and is always there. The per-card chip is the only design where the venue stays editable after planning — which you will want the first time someone books elsewhere at short notice.
  • C is the most content per pixel and the easiest to extend (top savers, stages, ledger), but nobody sees it unless they open stats. Weakest nudge, best payoff for stat nerds.
  • Mix — B's credits strip plus C's vault section is a real combination: a glanceable number everywhere, detail on demand. A does not combine with either.

OPEN QUESTIONS

  • Is €20/h a flat rate, or does it change by slot (peak vs off-peak, weekend)? A flat constant is one line; a rate table is a small config.
  • Who owns a saving — the person who planned the night, or everyone who played it? C's top-savers board only works with the first answer.
  • Does the pool ever reset (per season, per cash-out), or is it lifetime? A and C both show milestones, which implies cashing out.
  • docs/spec.md lists "no court/location field" as a decision and court booking as a non-goal. This reopens the smallest possible version of it — one boolean, no integration. Worth an explicit line in the spec rather than a silent contradiction.
